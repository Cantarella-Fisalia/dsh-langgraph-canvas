# dsh-langgraph-canvas双方协作协议

版本：1.0  
生效日期：2026-10-23  
项目目录：`E:\Heng\vis4agent`

本协议依据用户确定的分工编写：**甲方负责主要功能开发，乙方负责 DeepSeek Harness 接入与测试。** 本协议约束双方后续工作方式，不代表乙方已阅读确认，也不代表任何功能已经验收。

## 1. 角色与依据

| 角色 | 指代 | 核心责任 |
|---|---|---|
| 项目负责人 | 用户 | 产品目标、范围与优先级的最终决定 |
| 甲方：主功能开发方 | 当前 Codex 对话中的开发模型 | 前后端、LangGraph 能力、修改事务、扩展架构 |
| 乙方：接入与测试方 | 用户安排的另一模型 | Harness 适配、安装运行、集成测试、验收证据 |

文档职责：

- `PROJECT_PLAN.md`：定义产品需求、技术方案、阶段与验收目标。
- 本协议：定义人员分工、文件归属、接口协作和交付流程。
- `docs/DEVELOPMENT_HANDOFF.md`：记录当前实现状态和下一批交付。
- `packages/contracts/`：承载实际实现的版本化数据协议。
- `docs/evidence/`：保存可追溯的验证证据。

用户的后续指令优先。协议与主设计文档发生冲突时，先记录具体差异，再统一文档；不能以本协议自行扩大产品范围。尚未形成正式协议代码时，接口提案必须标为“拟定”。

## 2. 责任边界

### 2.1 甲方负责

1. 独立前端：项目选择、图画布、节点详情、配置、差异、运行观察。
2. 后端应用服务：项目管理、图 API、任务调度、编辑协调、事务、快照、冲突与撤销。
3. Python 工作进程：静态解析、源码映射、LibCST 转换、验证和项目运行事件。
4. 数据协议：图、编辑指令、任务、事件、诊断、能力描述及前端 API 客户端。
5. MCP、RAG、Tools、Skills 的公共接口、功能实现和项目运行能力生成。
6. 核心功能示例、开发启动与构建，以及必要的单元、模块和协议检查。
7. 修复归属上述模块的问题，提供乙方可实际执行的交付说明。

### 2.2 乙方负责

1. Harness 插件宿主与浏览器封装、界面挂载、资源装载和生命周期管理。
2. Harness profile、本地 bundle 安装、运行环境接入、打包和升级验证。
3. 将甲方的后端/前端接入 Harness，处理 API 前缀、宿主访问、资源路径和宿主鉴权衔接。
4. 实现 Harness 编码执行适配器：提交任务、指定工作目录、接收状态、取消和回传结果。
5. 在 Harness 中验证 Python 进程的启动、停止、重启及插件卸载后的清理。
6. 集成测试、端到端测试、交互与安装验收、环境兼容检查及回归测试。
7. 提交复现步骤、日志、截图和结果，修复归属接入层的问题。

“乙方负责测试”不免除甲方的基本验证责任。甲方不以“乙方会测试”为由交付未经基本检查的代码；乙方也不以“甲方本地通过”为由省略 Harness 实际验收。

### 2.3 容易混淆的责任

| 事项 | 甲方 | 乙方 |
|---|---|---|
| 前端页面和画布 | 开发并构建 | 挂载到 Harness，验证实际显示与交互 |
| 后端 HTTP/SSE | 实现服务和版本化协议 | 接入宿主路由、鉴权与连接，验证流式行为 |
| Python worker | 实现协议、解析与进程客户端 | 验证宿主环境启动、路径和生命周期 |
| Harness 编码任务 | 定义端口、上下文、任务状态与事务要求 | 实现宿主调用、取消和结果适配 |
| 代码写回 | 统一协调、冲突检测、应用和撤销 | 验证 Harness 任务不会绕过事务改原项目 |
| MCP/RAG/Tools/Skills | 实现领域接口、绑定与业务能力 | 验证宿主配置和可用服务的接入 |
| 核心依赖缺失 | 明确依赖和可复现安装方式 | 验证目标环境安装和兼容性 |
| API 或适配问题 | 修复核心处理错误 | 修复前缀、宿主权限、加载和协议转发错误 |

所有源码修改只通过后端修改协调入口执行。乙方的编码适配器应接受指定的临时工作区；未经明确设计不能直接把模型任务指向用户原项目并写回。

## 3. 文件与目录归属

“维护方”指默认修改责任，不代表另一方不能阅读。跨归属修改按第 5 节协调。

| 路径 | 维护方 | 说明 |
|---|---|---|
| `apps/frontend/**` | 甲方 | 独立前端，不在宿主客户端中堆积业务界面 |
| `apps/backend/**` | 甲方 | 应用、API、事务与通用基础设施 |
| `services/python-worker/**` | 甲方 | 解析、变换、验证与运行 |
| `packages/contracts/**`、`api-client/**`、`extension-sdk/**` | 甲方 | 修改影响接入时提供接口变更记录 |
| `extensions/**`、`resources/**`、`examples/**` | 甲方 | 核心扩展、模板与示例 |
| `plugins/harness/**` | 乙方 | 包括现有 `lib/index.js` 和 `client/client.js` |
| `adapters/harness/**`（若建立） | 乙方 | 独立宿主适配代码；不能把整个后端 adapters 目录划给乙方 |
| 各模块旁的测试、`tests/contracts/**`、`tests/fixtures/**` | 甲方 | 基本模块检查和共享协议样例 |
| `tests/integration/**`、`tests/e2e/**`、`docs/evidence/**` | 乙方 | 集成验收与证据；甲方提供需要的功能样例 |
| `scripts/dev/**`、`scripts/build/**` | 甲方 | 核心开发与构建 |
| `scripts/harness/**`、`scripts/test/**` | 乙方 | 宿主安装、启动和集成验证 |
| `PROJECT_PLAN.md`、本协议、`docs/architecture/**`、`docs/api/**` | 甲方 | 乙方通过交接记录提供接入事实和修订建议 |
| `docs/DEVELOPMENT_HANDOFF.md` | 甲方 | 汇总双方交付状态，不代替乙方验收记录 |
| 根目录清单、工作区配置、锁文件、`.gitignore`、共享构建配置 | 甲方协调 | 同一时段仅一方写入；乙方提出安装/打包所需变更 |
| `.dsh-test/**`、隔离 profile 和测试运行环境 | 乙方 | 非源码；主功能侧不直接改动 |

乙方可修改自己维护的插件包清单。根锁文件等共享文件有变动时，先登记写入范围，避免双方同时安装依赖产生覆盖。

接入适配器最终放置位置在首次实现前记录；一旦确定，归属表同步更新，不能形成两个重复适配器。

## 4. 接口协作

1. 甲方交付最小接口提案：用途、版本、输入输出、错误、事件、超时和取消、调用样例。
2. 乙方核对 Harness 的实际能力，给出可实现方式和限制；不把未经验证的宿主 API 当作已存在能力。
3. 双方以交接记录确认后，分别实现接口和适配器。确认是技术对齐，不要求用户反复批准常规实现。
4. 前端只访问后端协议；核心解析、编辑和事务不得直接依赖 Harness 私有对象。
5. 开发环境 API base URL 可配置；宿主挂载前缀由适配层处理。
6. 破坏性变更必须提前记录受影响端、迁移方式和验证项。修改协议时同时更新 Schema、客户端、样例和相关说明。
7. 模拟数据必须明确标记，不得用示例图、模拟任务或占位返回值冒充真实功能。
8. 两类能力作用域必须区分：开发助手能力与用户 LangGraph 项目的运行能力。

## 5. 共享工作区与变更协调

每批任务开始前，在交接记录中写明：任务 ID、负责方、涉及路径、交付目标、状态和前置依赖。双方读取最新记录后再开始写入。

- 不同时修改同一个文件；确需交叉修改，由默认维护方整合，或记录一次明确的临时移交。
- 不覆盖对方未提交内容；提交或同步前检查差异，不执行会丢失对方工作的 reset、clean 或强制覆盖。
- 生成的构建产物由构建命令更新，不直接手改；乙方记录实际加载的产物版本。
- 不自行更换目录、协议、核心依赖或实现路线来绕过尚未解决的接口问题。
- 跨边界小修也记录涉及文件和原因。经对方明确委托后可代修，但保留原维护责任。
- 对方尚未回复时，继续自己边界内且不依赖答复的工作；不把等待当成接口已获确认。
- 不自动操作用户正在使用的生产/桌面 profile；测试默认使用隔离环境。已有用户明确授权的操作按授权执行。
- Git 提交不是交付前提；无提交时用文件内容摘要和交付清单标识版本。

本协议不自动授权双方互发消息、创建新对话、操作账号或发布项目。需要这些操作时遵循用户已给出的授权和工具权限。

## 6. 每批交付与状态

任务状态统一使用：

`待开发 → 开发中 → 待接入 → 测试中 → 验收通过`

另有：`待修复`、`受阻`。开发完成只能标记“待接入”，不能代替“验收通过”。

### 6.1 甲方交付清单

- 任务 ID、对应主设计文档阶段、实现范围和未实现范围。
- 改动文件、协议版本、依赖与配置要求。
- 启动/构建/调用方法，至少一个真实输入输出样例。
- 基本检查的命令、结果和未验证事项。
- 乙方需要修改的接入点和预期行为。
- 验收场景、错误场景及已知限制。

### 6.2 乙方回传清单

- 使用的交付版本、Harness/Node/Python 等实际环境版本。
- 安装、启动、挂载和调用方法；说明真实数据或模拟数据。
- 每个验收项的通过/失败/未执行结果。
- 失败的最小复现、预期与实际结果、日志和相关证据。
- 建议归属：核心功能、接口、接入或环境；不确定时写“待定位”。
- 验收结论和剩余问题，不能仅报告“安装成功”。

建议双方分别新增记录，避免共同编辑同一交付记录：

- 甲方：`docs/handoffs/main/<任务ID>.md`
- 乙方：`docs/handoffs/integration/<任务ID>.md`

以上目录按需创建。甲方根据双方记录更新主设计文档与交接汇总；乙方可直接更新自己归属的证据和验收记录。

## 7. 缺陷处理和完成标准

乙方发现问题后先提供复现；甲方负责核心错误，乙方负责接入错误。无法定位时，分别检查后端独立调用与 Harness 调用的同一输入，使用关联任务 ID 对照结果。

甲方修复后注明影响范围，乙方复测相关路径。双方不为“让测试通过”擅自削弱验收条件、吞掉错误或跳过失败场景。

一个功能批次完成需要：

1. 甲方基本检查通过，交付资料完整。
2. 乙方在 Harness 中完成该批要求的验收并保存证据。
3. 阻塞该批目标的问题已解决，其他限制已记录。
4. 主设计文档与实现状态一致。

验收不是必须无任何限制，而是必须符合该批事先确定的范围和验收目标。截图只能证明画面，不能单独证明代码写回、事务或正确运行。
